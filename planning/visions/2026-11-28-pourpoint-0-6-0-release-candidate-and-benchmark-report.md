# Pourpoint 0.6.0 release candidate and benchmark report

## Outcome and release sequence

Deliver `0.6.0rc1` for external testing and a reproducible, consolidated `v0.5.0` versus release-candidate benchmark report before stable `0.6.0`. This vision is the implementation handoff for [issue #238](https://github.com/pourpoint-tools/pourpoint/issues/238). Publication leaves that issue open; implementation completes it when the release candidate is available on PyPI, stable documentation is verified unchanged, and the benchmark report and reproducible evidence are delivered. External-testing and report approval remain prerequisites for a separately authorized stable release, not permission to publish stable as part of this work.

The five tracks of the [overhaul vision](2026-11-28-pourpoint-0-6-0-correctness-performance-and-api-overhaul.md) are merged at `e274b50d5ee7e0c5ec8cc916d51e20787aee62c3`. The release baseline is `v0.5.0`, commit `efed954b9f65e05ed975f4ef0c963df14fdedf1f`. The package version remains `0.5.0` at this handoff.

Publish rc1 after correctness checks, package verification, prerelease documentation protection, and representative end-to-end smoke checks. The full benchmark report may follow rc1 while external testing proceeds independently. Do not claim release-wide speedups from existing track-specific measurements. Before stable `0.6.0`, the maintainer must review and approve both the consolidated report and external testing.

## Benchmark coverage and dataset limitations

Use real HFX 0.4.0 data, with exact publication identities and workload settings recorded. Required comparisons cover both TDX vector workflows and GRIT vector/raster workflows. Access and cache completeness still need verification; recorded delivery receipts are not fresh live-access checks.

- **TDX Hydro:** use the private Hetzner connectivity-enabled delivery at `s3://pourpoint-hfx/tdx/hfx-0.4.0/NGA-TDX-Hydro-20230126-full62-20261121/`. Its recorded manifest SHA-256 is `787ccdd094764c0a4d8724e4bb2cc9a06ca6c5a48996a3ae01da3b0866b16e8c`. [HFX #289 delivery](https://github.com/pourpoint-tools/hfx/issues/289#issuecomment-7062414732) verifies catchment connectivity and coverage safeguards. This supports vector-only delineation, not raster refinement. Do not use the superseded `full62-20261027` bundle's missing connectivity as evidence that current TDX delineation is unsupported.
- **GRIT:** use the public R2 delivery at `https://basin-delineations-public.upstream.tech/grit/hfx-v0.4.0/`. Benchmark whole-subbasin workflows and raster refinement separately. [HFX #269's resolved provenance finding](https://github.com/pourpoint-tools/hfx/issues/269#issuecomment-7104717277) confirms a GRIT v1.0 raster-merge defect that creates closed drainage loops. Refinement can leave holes and understate contributing area; `refine=False` avoids these raster directions. GRIT remains useful for performance and software-regression comparisons, but agreement between Pourpoint versions does not establish hydrologic correctness. Do not repair or substitute rasters silently.
- **Optional MERIT sample:** if the existing private delivery is accessible, add a small real-data refinement sample with verified complete upstream coverage. The delivery is `s3://pourpoint-hfx/merit/hfx-0.4.0/merit-hydro-v1.0.1-basins-v1.0-bugfix1-20261118-connectivity-candidate/`, recorded manifest SHA-256 `9d3d48af7fe6f1dbd9661621cba307d662e6a35eee65f7de3911a6c31edecb2d`; the `candidate` suffix was retained on [approval as the current private delivery](https://github.com/pourpoint-tools/hfx/issues/285#issuecomment-7008056957). Some closures are incomplete; [HFX #292](https://github.com/pourpoint-tools/hfx/issues/292) records affected smoke cases. Do not relax completeness checks to obtain successful samples. MERIT is not a release prerequisite or a global correctness certification.

Choose representative regions and sizes: hillslope/small, alpine/medium, and mainstem/large, including genuinely large multi-thousand-subbasin vector/export work. The previous 39-subbasin Spain mainstem refinement measurement does not establish large-vector or large-export performance. Select exact targets and supported combinations during implementation rather than forcing identical operations onto datasets that lack them.

Cover cold application caches, warm online and warm offline reuse, single targets, and multi-target batches with sequential and parallel `n_jobs`. Distinguish reopened persistent-cache reuse from same-reader reuse. Measure complete supported workflows, including nearby river selection, snapping, delineation, watershed river selection, and `QGISBundle.write`; include refinement only where rasters are supplied. Account for initialization and preparation rather than timing only preloaded kernels.

## Evidence and interpretation

Produce runnable scripts, workload definitions, retained machine-readable results, and a consolidated report under `planning/experimentation/`. Keep credentials and private dataset contents out of published evidence. Record code revisions, dataset identities, environment, machine resources, targets, operation settings, cache state, and reproduction commands. Compare the actual release-candidate code with `v0.5.0`; if later fixes change measured paths, identify and refresh affected measurements rather than labeling an older commit as the candidate.

Measure total and stage wall time, process peak RSS, peak Python allocations, HTTP/object request counts, transferred payload bytes, and SQLite cache disk consumption including relevant sidecars. Keep timing, allocation profiling, and correctness checks separate where instrumentation changes performance. Describe repetitions and variability, measurement boundaries, and unavailable observations. Do not present a fresh application cache as proof of a cold OS or remote CDN cache.

Compare equivalent logical outputs, including geometry, selected identities and source attributes, coverage diagnostics, and exported content/provenance where semantics match. Account explicitly for intentional API/default/export changes rather than demanding byte-identical GeoPackages. Use equivalent explicit settings for controlled comparisons and explain any default-behavior comparison separately. Do not patch the old release silently to make a workload pass, or treat its outputs as unquestionable ground truth. Investigate mismatches; explain floating-point differences with appropriate geometric evidence rather than accepting a small area difference alone as proof of equivalence.

The existing [overhaul experimentation log](../experimentation/2026-11-28-pourpoint-0-6-0-correctness-performance-and-api-overhaul.md) contains useful seeds, not the requested consolidated comparison: storage/refinement numbers compare intermediate revisions, and snapping/export measurements are synthetic. Existing `scripts/measure_delineation.py`, `scripts/measure_delineation_warm.py`, `scripts/compare_delineation.py`, and `scripts/measure_fabric.py` may supply useful pieces but are not a ready release-comparison harness. In particular, the warm script references a missing `docs/receipts/grit-delineation-targets.json`; recover and record exact workloads rather than assuming those scripts run unchanged. Older giant-union experiments are optional stress evidence, not substitutes for full workflows on the current publications.

Profile remaining hotspots. Distinguish Pourpoint implementation costs, dataset defects/coverage limits, and demonstrated HFX 0.4.0 format limitations. A hotspot alone does not prove a format redesign is required. Preserve the canonical input contract at `../hfx/docs/site/index.md`.

## Acceptance and resource principles

**Suitability for 16 GB laptops is a core Pourpoint design principle**, not merely a benchmark condition. Evaluate representative large workflows against that envelope, leaving room for the operating system and normal application use. Report actual process memory and any excluded or unsuccessful workloads. A successful run on a high-memory machine does not establish laptop suitability; larger stress cases must be distinguished clearly. Exact measurement mechanisms remain implementation choices, and no new paid infrastructure is authorized by this vision.

New correctness or integrity failures block publication. Bring material time or memory regressions to the maintainer for a decision; do not silently accept them or expand this into another optimization overhaul. Not every workload must improve. Preserve incomplete-coverage safeguards, source fidelity, and the distinction between expected source-data limitations and new engine regressions.

Dataset repair, a broad hydrologic certification campaign, and HFX `0.5.0` redesign are outside scope. Do not reopen the overhaul's unpaged SQLite cache and pure Python/NumPy packaging choices merely to conduct these comparisons.

## Release preparation and documentation protection

- Set the package version to `0.6.0rc1` in `pyproject.toml` and refresh `uv.lock`; frozen CI must work. Run project checks using `uv`, Ruff, ty, and pytest under the repository's test-first guidance.
- Verify that `docs/hfx-revision` identifies the intended HFX documentation revision. At handoff it is `2fcdaf55e25b1fa49a6c5e69edb5147d172c1721`; do not update it merely to follow a moving branch.
- Run `uv build` and inspect wheel/sdist metadata and contents, including source/wheel exclusions. Retain the pure-Python `py3-none-any` distribution approach selected by the overhaul.
- Protect prerelease documentation in `.github/workflows/publish-pypi.yml` and, as needed, `scripts/publish_docs.py` and `tests/test_docs.py`. Build and retain inspectable release docs artifacts, but a GitHub prerelease must not modify **either `main` or `gh-pages`** in `pourpoint-tools/pourpoint-tools.github.io`. The current script always pushes site `main`; `DOCS_PUBLICATION_ENABLED` gates only `gh-pages`, so that switch alone does not satisfy the requirement. Preserve the intentional stable-release publication gate and verify prerelease behavior before publishing rc1.
- Prepare release notes covering qualified performance evidence, new composable APIs, and migration details: `FootprintRefinement.footprint` becomes `.geometry`; `GranularRefinement.geometry` is exposed and its QGIS export includes `watershed`; remote caching defaults to `cache="auto"`; `vectors.gpkg` stores collective `source_arrow` streams with `kind="features"` / `kind="nodes"`; and single-row `Feature` / `ClippedRiver` comparison and hashing replace whole-table behavior. Link the overhaul vision for full API details and state dataset limitations.
- Publish `v0.6.0rc1` as a GitHub prerelease, verify `pourpoint==0.6.0rc1` is available and installable from PyPI, and verify stable-site branches remain unchanged by the prerelease workflow. External user testing starts once the candidate is live.

Do not publish final `v0.6.0` in this work. Deliver the report and candidate handoff for maintainer review, with remaining limitations and decisions visible.
